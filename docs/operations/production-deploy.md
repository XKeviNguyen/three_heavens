# Production deployment and rollback

## Pre-deploy

1. Confirm the intended release SHA and review every migration in the release range.
2. Confirm a recent successful completed bundle has been copied to approved encrypted off-host storage. For a risky migration, require a fresh restore-verified backup. Confirm that `RAILS_MASTER_KEY` (and `SECRET_KEY_BASE`, if set) is recoverable from the separately protected secret store, without printing it; see [encryption root secrets](backup-and-restore.md#encryption-root-secrets).
3. Run `bin/ops/preflight` in the candidate production runtime. It prints variable names/statuses only, checks the four databases independently, checks storage configuration/writability, verifies `pg_dump`/`pg_restore`, pending migrations, Solid Queue configuration, recurring schedule parsing, and eager loading, and never calls OpenRouter. `--json` provides the same bounded fields.
4. Confirm mail delivery configuration: `MAIL_FROM`, `SMTP_HOST`, and optional `SMTP_PORT` are set in the deploying shell, and `SMTP_USERNAME` and `SMTP_PASSWORD` resolve in the Kamal secrets. Production refuses to boot without them, so a missing value stops the deploy before the new container serves traffic. Never put SMTP credentials in `config/deploy.yml`, documentation, or a committed secrets file.
5. Confirm Sign in with Google configuration: `GOOGLE_CLIENT_ID=<production Web OAuth Client ID>` is set in the deploying shell (`config/deploy.yml` passes it as clear environment; it is a public identifier, and this identity-only flow uses no client secret). It must be the production OAuth client, not the localhost development client, and that client must list exactly `https://APP_HOST_PLACEHOLDER` as an Authorized JavaScript origin and `https://APP_HOST_PLACEHOLDER/auth/google/callback` as an Authorized redirect URI, where `APP_HOST_PLACEHOLDER` is the canonical production `APP_HOST`. Preflight reports `google_client_id: unavailable` and fails when it is missing or malformed.
6. Confirm the `three_heavens_storage:/rails/storage` Kamal volume is attached and writable by uid/gid 1000.
7. Confirm `/up`, `/ready`, queue processing, and the old environment's admin Operations diagnostics are healthy enough for deployment.
8. Determine code/schema rollback compatibility. Do not deploy a destructive same-release schema removal. Use expand, deploy compatible code, migrate/backfill, then contract in a later independently backed-up release.

    Check that the release's migrations fit in Kamal's `deploy_timeout` (30 seconds by default), because they run inside the new container's boot. For the bring-your-own-key and product tour release, the first five of its seven migrations took 2.9 seconds (4.0 seconds including Rails boot) on a disposable PostgreSQL 17 copy of the v1.1.0 schema with 100,000 synthetic rows in `users` and in each of the ten billed tables, and 26.8 seconds (28.1 seconds, leaving no margin once the web server starts) with 1,000,000. Time grows with rows: about 17 seconds per million `users` rows for the product tour backfill, which holds an ACCESS EXCLUSIVE lock on `users` throughout, and under 1 second per million rows in each billed table for constraint validation and concurrent indexing (9 seconds for all ten at 1,000,000 rows each). The two page-guide migrations (`20261012090000` and `20261012100000`) add 0.05 seconds at 100,000 `users` rows and 0.36 seconds at 1,000,000; the second validates a CHECK constraint under an ACCESS EXCLUSIVE lock on `users`. The full list is in the [V1 readiness record](../releases/v1-final-readiness.md#migrations-pending-in-production). Before deploying, read the row counts (`SELECT relname, n_live_tup FROM pg_stat_user_tables`) and look for long-running transactions (`pg_stat_activity`), which a concurrent index build waits for. If `users` or any billed table is far beyond 100,000 rows, or a long transaction cannot be ended, stop and plan the migration as a separate step instead of raising the timeout by guesswork.
9. Configure the edge proxy to reject request bodies larger than 21 MiB. This permits the supported Translation Reference request containing two files of at most 10 MiB each plus 1 MiB of multipart overhead; per-file application validation remains authoritative. The application gives 21 MiB only to the two upload forms and smaller per-route limits to every other request (64 KiB by default; see [security](../security.md#request-and-input-limits)), enforced before parsing for declared bodies and while reading undeclared ones, but the proxy remains the first line of defense for chunked requests without `Content-Length`. The proxy limit is not the JSON limit: the application separately limits JSON bodies to 512 KiB for the workspace draft autosave and 8 KiB elsewhere, and bounds their structure, because they are parsed before authentication.
10. Deploy the web container only through `config/deploy.yml`, which limits its kernel socket buffers (`--sysctl net.ipv4.tcp_rmem` and `tcp_wmem`, at most 256 KiB). Every request body Puma reads costs socket buffers, freed allocator memory, and tempfile pages; the image makes jemalloc return freed memory at once (`MALLOC_CONF`), and the socket limits keep many simultaneous bodies within a small container. Without them, 80 simultaneous 30 MiB chunked requests exhausted a 768 MiB container and killed the web process. These `net.*` sysctls are set in the container's own network namespace, which Kamal's network provides; Docker refuses them in the host's namespace, so a container started with `--network host` and these options does not start at all (`sysctl "net.ipv4.tcp_rmem" not allowed in host network namespace`). Do not run the web container on the host network. `script/breakers/chunked_request_memory.rb` reproduces the measurements against a locally built image, including signed-in hostile PDF uploads during a chunked flood (scenario `pdf_chunked`). In the V1.1 stabilization run (768 MiB, no swap): 80 or 200 simultaneous 30 MiB bodies, malformed framing, slow senders, disconnects, three 30-second hostile PDF floods (each PDF holding the single worker slot for its full 5 seconds or inflating to the worker's 256 MiB limit) with 80 chunked bodies at once, and 10 waves of 80 bodies left the same Puma process serving `/login` (200 throughout; at most 7 s under the combined flood), no OOM kill, no PDF worker left running, a normal PDF import succeeding afterwards, and Puma's memory back to 180 to 300 MiB after every wave. Rejected bodies are answered 413 (or 400 for invalid framing) by Puma or Rails; when Puma closes the connection while Thruster is still forwarding the body, or the client's chunk framing is invalid, Thruster's Go reverse proxy reports 502 or the socket is reset instead. Those are transport outcomes, not application responses. In production kamal-proxy buffers each request body and rejects oversized ones itself (see the edge evaluation in `docs/operations/edge-proxy-evaluation.md`), so such bodies do not reach Thruster.
11. Keep the client-address chain intact. Password sign-in throttling (`SignInThrottle`) and the other per-network limits key on `request.remote_ip`, which Rails derives as the nearest X-Forwarded-For entry outside its default private/loopback trusted ranges; IPv6 clients share their /64's budget. The application removes any Client-Ip header and never reads CF-Connecting-IP or True-Client-IP. `config/deploy.yml` encodes the only supported topology, the Cloudflare Tunnel: browser → Cloudflare, which terminates TLS → cloudflared on the `kamal` Docker network → kamal-proxy on port 80 → Thruster → Puma. Cloudflare appends the address it received the connection from to any client-supplied X-Forwarded-For. kamal-proxy forwards that header (`proxy.forward_headers: true`, with `proxy.ssl: false`) and appends cloudflared's private address; Thruster appends kamal-proxy's. The nearest untrusted entry is therefore the visitor Cloudflare saw, and entries a client adds stay further left. Without forwarding, kamal-proxy replaces the header with cloudflared's address, so every visitor shares one budget per limit: 10 sign-in attempts in 3 minutes from anyone block password sign-in for everyone, and registration, confirmation resends and Google sign-in are shared the same way (headers still cannot choose the address).

    Forwarding is safe only while cloudflared is the only route to kamal-proxy, so `proxy.run.publish: false` boots kamal-proxy with no host port. These three settings are requirements, not defaults to override: do not change them in a Kamal destination file or a local edit, and never expose kamal-proxy directly, because a directly reachable kamal-proxy that forwards headers lets every client choose its own address through X-Forwarded-For. Serving browsers directly would need `ssl: true`, no forwarding, published ports and a new evaluation. `test/config/production_deployment_contract_test.rb` fails if the commands Kamal renders publish a kamal-proxy port, enable TLS at kamal-proxy, stop forwarding, or change the kamal-proxy version evaluated below. The topology also assumes that no other public hostname and no other container on the `kamal` network relays outside traffic to kamal-proxy, and that Cloudflare's Pseudo IPv4 is not set to Overwrite Headers, which replaces IPv6 visitors' addresses with hashed IPv4 addresses and loses the /64 grouping.

    Before the first deploy with this configuration, confirm on the host without changing anything: `docker inspect kamal-proxy --format '{{json .HostConfig.PortBindings}}'` shows no binding (`{}`), since otherwise this deploy turns on forwarding on a public port; `docker network inspect kamal --format '{{range .Containers}}{{.Name}} {{end}}'` lists cloudflared, and nothing that relays outside traffic; and `docker ps --format '{{.Names}}'` shows this application's containers as `three_heavens-web-<version>`, with no destination suffix. If any of these differs, reconcile the running deployment with `config/deploy.yml` before deploying. Unpublished must also mean unreachable from other machines: a machine that can route to the `kamal` network could reach kamal-proxy's private address and choose its own client address. Whether Docker blocks that depends on the engine version, the network's gateway mode and trusted interfaces, and the daemon's flags and configuration files, so do not rely on it. Before deploying, the host needs its own firewall rule, restored at every boot, that drops new forwarded connections into the `kamal` network from anywhere but that network. With Docker's iptables rules, that is `iptables -I DOCKER-USER ! -i BRIDGE -o BRIDGE -m conntrack --ctstate NEW -j DROP`, and the same with `ip6tables` if the network has IPv6. If `DOCKER-USER` does not exist (Docker's iptables management is turned off), insert the rule at the top of `FORWARD` instead; with Docker's nftables backend, add an `inet` table chain on the forward hook at priority `filter - 1` containing `iifname != "BRIDGE" oifname "BRIDGE" ct state new drop`. `BRIDGE` is the `kamal` network's bridge interface: `br-` plus the first 12 characters of `docker network inspect kamal --format '{{.Id}}'`, unless the network sets `com.docker.network.bridge.name`. Confirm it with `ip link show BRIDGE`, and redo the rule whenever the network is recreated, because the name changes. Connections between containers on the network, the containers' own outbound connections and their replies, and the host's own connections are unaffected; ports published by containers on `kamal` become unreachable from other machines, which this application does not use. Make sure no rule added later, for example by VPN software, accepts that traffic before this one. Verify the rule, not the configuration: from another machine on the same private network, with a route to the `kamal` subnet through this host, `curl --max-time 5 http://KAMAL_PROXY_ADDRESS/up` must time out without any HTTP response while `tcpdump -ni any host KAMAL_PROXY_ADDRESS` on this host shows the probe's SYN packets arriving and no reply, which shows that the probe reached the host. Docker's own filtering may drop the probe before the rule does; the rule is still required, for the configurations where Docker does not. `KAMAL_PROXY_ADDRESS` is the output of `docker inspect kamal-proxy --format '{{(index .NetworkSettings.Networks "kamal").IPAddress}}'`; if the network has IPv6, repeat the probe with `.GlobalIPv6Address` in place of `.IPAddress` (in brackets in the URL). Every other application deployed behind the same kamal-proxy must also set `proxy.run.publish: false`, because Kamal checks run settings only within one `config/deploy.yml`, and another application's `kamal proxy reboot` without them publishes ports 80 and 443.

    Kamal applies `proxy.run` only when it creates the kamal-proxy container (the first `bin/kamal setup` or `bin/kamal deploy` on a host, or `bin/kamal proxy reboot`); a deploy reuses a running kamal-proxy as it is, so one started earlier with published ports keeps them. `ssl` and `forward_headers` are applied on every deploy and rollback, from the checkout Kamal runs in: roll back with `bin/kamal rollback` from a checkout of the current `config/deploy.yml`, and never deploy an earlier commit to roll back, because the proxy settings of releases before this configuration (`ssl: true`, no forwarding) make kamal-proxy redirect the tunnel's plain-HTTP requests to HTTPS, which loops, and every visitor share one rate-limit budget. After a deploy, or any proxy change by any application on the host, check without signing in: on the host, `docker inspect kamal-proxy --format '{{.HostConfig.NetworkMode}} {{json .HostConfig.PortBindings}}'` must show the `kamal` network and no binding (`{}`), and `docker exec kamal-proxy sh -c 'cat $HOME/.config/kamal-proxy/kamal-proxy.state' | tr ',' '\n' | grep forward_headers` must show `true` (this is the state file of kamal-proxy v0.9.2). If a port is bound, first confirm that cloudflared reaches kamal-proxy over the `kamal` network, not through that port, then schedule `bin/kamal proxy reboot`, which briefly interrupts every application behind that proxy. Then load `/login` once in a browser and confirm that `bin/kamal app logs --grep 'Started GET "/login"'` shows that browser's public address, not a private `172.x` or `10.x` address. kamal-proxy's own request log is not evidence: its `remote_addr` field shows the X-Forwarded-For client even when kamal-proxy does not forward the header.

    Evidence: the kamal-proxy, Thruster, Go `httputil` and Rails sources; header-shape tests (`test/integration/login_throttling_test.rb`); and `script/evaluations/cloudflare_tunnel/run.sh`, which runs kamal-proxy with the image and deploy command Kamal renders from `config/deploy.yml` in front of the real image and exits nonzero unless every visitor keeps their own address and sign-in budget and a control with forwarding off makes them share one (`test/script/cloudflare_tunnel_evaluation_test.rb` tests its expectations and its bounded readiness waits). It passed on 2026-10-11 with kamal-proxy v0.9.2 and an image built from this change merged with develop at `ea82c69`: X-Forwarded-For, Client-Ip, True-Client-IP and CF-Connecting-IP values that rotated or claimed another visitor's address did not change the client address, a visitor's 11th failed sign-in was throttled, a distinct visitor and a victim of another visitor's spoofed attempts kept their own budgets, and with forwarding off every visitor appeared as the cloudflared stand-in and the second visitor's first sign-in was refused. With `forward_headers: false` in `config/deploy.yml` it failed. Cloudflare's own header handling is taken from its documentation, not reproduced. The direct-TLS configuration of earlier releases was evaluated separately (`docs/operations/edge-proxy-evaluation.md`). Each account also has a budget that rotating addresses cannot extend. A browser that has signed in to that account before (device cookie) has its own budget, so failed attempts from elsewhere can keep blocking password sign-in only on browsers new to that account, for as long as they continue; Google sign-in is unaffected.

Sign-in sessions are stored server-side (the `sessions` table) from v1.1. Signing out deletes that browser's row, so a copied cookie stops working, while other browsers stay signed in. Signing in again in the same browser, with a password or with Google, ends the session it replaces. A row authenticates for 30 days after sign-in at most; `SessionCleanupJob` deletes expired rows hourly. Disabling an account through the model (`user.update!(status: "disabled")`) deletes its rows, and a sign-in racing the disable waits on the account row and then starts no session; `update_all` or SQL skips that, so delete `user.sessions` explicitly if you disable that way. A sign-in whose response is lost, or that races a sign-out in the same browser, can leave a row that no browser holds. Such a row authenticates only with a cookie the server sent and the browser discarded, expires with the others, and is bounded like every session row by the sign-in rate limits: at most 10 password sign-ins and 10 Google callbacks per 3 minutes per client network, so at most 288,000 live rows (about 26 MB at the measured 96 bytes per row with indexes) per network over 30 days. Google sign-in finishes on a same-site redirect (`/auth/google/complete`) so the browser sends its session cookie; after deploying, confirm on staging in a real browser that signing in with Google while already signed in leaves exactly one row for that browser. Cookies issued by earlier releases carry no row, so every user signs in again once after this deploy. Rolling back to an earlier release does the reverse: v1.1 sign-ins are lost, and pre-v1.1 cookies that were not replaced authenticate again.

## Deploy

Use the repository's installed Kamal command from a trusted operator workstation after supplying the variable names documented in [production configuration](configuration.md):

```sh
bin/kamal deploy
```

Deploy with no destination (`-d`): `config/deploy.yml` is the complete production configuration, including the proxy settings of step 11. A destination file would be merged over it and would also rename the service's containers and its kamal-proxy service, so it would not replace the running deployment in place.

Kamal Proxy uses `/up` for lightweight container liveness. The image entrypoint runs `bin/rails db:prepare`; a failed migration stops startup/deployment. Do not automatically run `db:rollback`. Inspect schema and migration state before correcting and retrying. Never edit files inside a running production container.

This repository does not create a large backup automatically in a deploy hook: backup storage availability and freshness are explicit operator prerequisites, and brittle hook behavior must not obstruct incident recovery.

The recurring operations queue removes expired SourceImports and unused workspace submissions hourly, clears finished queue records hourly, reconciles stale work, and removes only unattached Active Storage blobs older than seven days once daily. Structured application events are emitted to standard output; configure a bounded retention policy in the deployment log collector because the application does not own external log storage.

## Post-deploy

Run the credential-free endpoint and dependency smoke command from the deployed runtime:

```sh
bin/ops/post-deploy-smoke https://APP_HOST_PLACEHOLDER
```

Then verify `/up`, `/ready`, the admin-only aggregate Operations diagnostics, Solid Queue processing and recurring schedules, and structured one-line JSON events. Exercise an authenticated no-provider workflow if incident policy permits. Do not automatically submit source content, enqueue paid work, or call OpenRouter as a smoke test.

`/up` means process boot only. `/ready` means primary database web readiness only. Cache, cable, queue, and storage state belong to preflight, smoke, admin diagnostics, and logs so an auxiliary outage does not silently change load-balancer semantics.

Health probes and Host authorization:

- **Kamal Proxy liveness:** `/up` is exempt from Host authorization, because Kamal Proxy reaches the container by address.
- **Public readiness:** probe with Host `APP_HOST`, for example `bin/ops/post-deploy-smoke https://APP_HOST_PLACEHOLDER`.
- **Internal readiness:** probe from inside the container over loopback, for example `docker exec CONTAINER_PLACEHOLDER curl -fsS http://127.0.0.1:3000/ready`. Only a raw `Host` header of `localhost`, `127.0.0.1`, or `[::1]` (optionally with a port) qualifies, and never on a request that carries `X-Forwarded-Host`.
- **Refused hosts:** any other Host, such as a container IP or an unknown name, receives `403` on `/ready` and on every application path. Probing `/ready` through a container IP therefore reports `403` by design.
- **Pre-promotion checks:** a quiescent or pre-promotion environment must be checked with the loopback probe, or with an explicit `Host: APP_HOST` header.

## Rollback

A code rollback and a database rollback are different operations. Never roll back past the OpenRouter bring-your-own-key release; roll forward instead (see below).

```sh
bin/kamal rollback RELEASE_VERSION_PLACEHOLDER
```

Kamal can select an earlier application image; it does not reverse migrations. Roll back code only when the earlier code is compatible with the current schema. Never automatically run `db:rollback` in production. If schema state is uncertain, stop, inspect `bin/rails db:migrate:status`, review the exact migration transaction outcome, and choose a forward fix or separately reviewed database recovery procedure. Restoring a backup is disaster recovery with potential data loss, not a routine code rollback.

Code from before the OpenRouter bring-your-own-key release does not know who pays for AI work, so the database fences it out (migration `20261010090100`):

- The AI run tables have no `billing_source` default, so that code cannot create runs. Starting AI work, or an automatic workflow advancing to its next stage, fails before anything is scheduled.
- That failure also stops automatic workflows that need no new run. The earlier `Pipelines::Reconcile` advances each pipeline inside one transaction, oldest `last_reconciled_at` first, and lets the not-null error escape: the transaction rolls back without recording the attempt, the whole batch stops, and every run of the recurring `PipelineReconciliationJob` (every 10 minutes) fails again on the same pipeline. While any workflow is due to start a paid stage, no workflow behind it advances, even to a free step such as reaching the editor.
- `enforce_ai_provider_attempt_payer` refuses a provider attempt whose payer differs from its run's. That code therefore cannot claim personal-key work; its claim fails before any provider request, and the run is failed later by stale-work reconciliation (`stale_pending`, or `stale_execution` for a retry) so its owner can retry explicitly.

Consequences:

- During the deploy that applies this migration, the old container fails AI starts from the moment the migration commits until traffic switches to the new container. Deploy at a quiet time.
- The release's migrations commit one at a time while the new container boots, and Kamal (2.12) stops a container that is not healthy within `deploy_timeout`, 30 seconds by default. A timeout or failure after `20261010090100` commits leaves the old container serving on the fenced schema: AI starts fail and automatic workflows stall as above, with no data lost and nothing billed to the wrong payer. Redeploy the same release promptly: first confirm in `pg_stat_activity` that no migration statement from the stopped container is still running (a stopped container does not cancel its server-side statement, which keeps its locks), then deploy; the remaining migrations resume safely (`20261010090300` rebuilds an index left invalid).
- **Roll forward only.** Do not run `bin/kamal rollback` to a release before the bring-your-own-key release, and do not run `db:rollback` on these migrations: an image rollback leaves AI starts failing closed and automatic workflows stalled, and a database rollback would also discard users' saved keys and payment choices. Fix forward with a new release instead.
